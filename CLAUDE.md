# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`AGENTS.md` holds the repository conventions (naming, commit style, PR expectations) and applies here as well.

## Commands

- `npm run dev`: Turbopack dev server on http://localhost:3000. It sets `NODE_OPTIONS=--network-family-autoselection-attempt-timeout=2000` because Node's default 250 ms connect attempt times out on slow networks, which made requests fail at random. Use the same flag for `next start` and Node scripts.
- `npm run lint`: ESLint (flat config in `eslint.config.mjs`)
- `npm run build`: production build with Turbopack
- `npm run import:woocommerce -- --dry-run`: preview a re-import of the WooCommerce export (`kachabiti-products.csv`); drop `--dry-run` to write. It is idempotent: products are upserted by slug, variants are matched by color + size and updated in place (never touching stock), and images and discounts are replaced. English/French text lives in `scripts/import/translations.json` and `descriptions.json`, and color hexes in `colors.json`.
- Local copy in Docker (docs/DOCKER.md): `npm run docker:env`, `docker compose up -d db storage`, optionally `npm run docker:import` (copies a database read-only, e.g. the server's), then `npm run docker:up` (web on :3000, NestJS on :4000, Postgres on :5433, files on :9000).
- `cd api && DATABASE_URL=… node scripts/migrate.mjs [--dry-run]`: apply the migrations in `supabase/migrations` the database doesn't have yet (recorded in `supabase_migrations.schema_migrations`).
- Production (docs/DEPLOY.md): Terraform in `infra/terraform/` (one AWS EC2 server running the API, Postgres and Caddy; S3 buckets; disk snapshots; a budget alert), server files in `deploy/` (`docker-compose.prod.yml`, `deploy.sh`, `backup.sh`), GitHub Actions in `.github/workflows/` (`ci.yml` on PRs and pushes to `main`; `deploy.yml` on push to `kachabiti-nest`: CI, then the API only when it changed, with no downtime). Vercel skips site builds for backend-only pushes (`vercel.json`). An empty database is built from `db/baseline.sql` by `api/scripts/migrate.mjs`.
- `node scripts/db/move-database.mjs`: copy a whole database to another Postgres (`SOURCE_DATABASE_URL` → `TARGET_DATABASE_URL`) and compare row counts; used for the move off Supabase and for backups/restores.
- `npx tsc --noEmit`: type-check. **Run this yourself**: `next.config.ts` sets `ignoreBuildErrors` and `ignoreDuringBuilds`, so `npm run build` succeeds even when there are type or lint errors.

The repo has no test runner. To verify a change, run lint and a type-check, then exercise the affected localized, admin, and API routes in the dev server.

## Architecture

Kachabity is a Next.js 15 App Router storefront for handcrafted Tunisian products. It uses React 19, Tailwind v4 and Ant Design 6 (with `@ant-design/v5-patch-for-react-19`). Every `/api` request is served by the NestJS app in `api/` (see **NestJS API**), on plain Postgres 17, with files in S3-compatible storage (AWS S3). Supabase is no longer used. The site deploys on Vercel and the API on one AWS server, as described in docs/DEPLOY.md.

### Routing and middleware

`middleware.ts` handles two separate jobs:

1. **Back-office gate (roles and permissions).** Requests to `/admin/*` (except `/admin/login`) and back-office API requests resolve the user from the session cookie (`kb_access`, verified locally; see **Accounts and sessions** below), so roles come from the token. `lib/admin-auth.ts` defines the model:
   - `getAdminRole()`: `'owner'` if `app_metadata.role` is `'owner'` or the email is in `OWNER_EMAILS`; `'admin'` if `app_metadata.role` is `'admin'` or the email is in the comma-separated `ADMIN_EMAILS` env var; `'staff'` if `app_metadata.role` is `'staff'`; otherwise none. Owners and admins have full access (`hasFullAccess`). Only owners can give the owner role or change or delete an owner. Never trust `user_metadata`, because users can edit it themselves.
   - `getPermissions()`: admins have every permission in `PERMISSIONS` (`products`, `stock`, `orders`, `discounts`, `marketing`, `analytics`, `costs`, `customers`, `pos`, `purchasing`, `finance`, `delete`, `hard_delete`) plus team management. Staff have the list in `app_metadata.permissions`, or `DEFAULT_STAFF_PERMISSIONS` when there is none. Admins edit these lists in Admin → Team (`/api/admin/team`). Changing a member's role or access closes their sessions and applies within 15 minutes.
   - API rules live in `apiRequirement()` (`lib/api-access.ts`), applied by the NestJS guard together with each route's decorator: `MUTATION_PERMISSIONS` for writes to catalog/marketing APIs, explicit rules for `/api/stock/*`, `/api/sales/*`, `/api/admin/*` and the rest. A DELETE needs the area permission **and** `delete`; `/api/admin/team` is admin-only, and `{ owner: true }` (`/api/owner/*`) is for owners only. Refused API calls get 401/403 and are logged by the guard. `requirementFor()` in `middleware.ts` gates admin pages only (`PAGE_PERMISSIONS`): refused pages redirect to `/admin/dashboard` and are logged through `POST /api/admin/access-denied`.
   - The sidebar (`menuItems` in `app/admin/layout.tsx`) is grouped: "My work" (agents' daily screens) first, then Owner, Money, Catalog, Stock & purchasing, Marketing, Administration. `menuFor()` hides entries a person can't open and drops empty groups.
   - NestJS handlers read the verified identity with `@CurrentActor()` (back office) or `@CurrentUserId()` (any signed-in user). The admin UI uses `useAdminRole()` (`lib/admin-role-context.tsx`, fed by `GET /api/admin/me`) and its `can(permission)` only to hide menu entries and controls.
   - The same session serves the admin and the storefront (see below). Writes to `/api/*` whose `Origin` names another host are refused with 403 (`foreignWrite`), on top of the `SameSite=Lax` cookies.

**Accounts and sessions** (NestJS, `api/src/auth/auth.controller.ts`, `/api/auth/*`; Supabase Auth is no longer used). Accounts are rows of `public.users`: `email`, `password_hash` (bcrypt; the hashes were copied from Supabase Auth at the switch), `app_metadata` (`role`, `permissions`), `user_metadata` (what the customer typed: `full_name`, `phone`, `address`, `city`, `country`), `email_confirmed_at`. The public can read only `id, name, avatar_url` of it.
- Sign-in sets two httpOnly cookies (`lib/auth-session.ts`): `kb_access`, a 15-minute HS256 JWT signed with `AUTH_SECRET` (sub, email, app_metadata), and `kb_refresh`, a random token whose sha256 is a `user_sessions` row (30 days, extended on use, not rotated). When `kb_access` has expired, middleware calls `POST /api/auth/refresh` and passes the new cookie on, so pages and API routes always see a live session; roles are re-read at each refresh.
- Sessions are revoked at sign-out, on a password change (the other sessions), a password reset (all of them), and when the Team API changes, removes or deletes a member.
- Sign-up e-mails a confirmation link when SMTP (`GMAIL_*`) is set; without it (local) accounts are confirmed at once. Confirmation and reset links are single-use `auth_tokens` rows (sha256 of the token; 24 h and 1 h), e-mailed in en/fr/ar; without SMTP on a local machine the link is printed in the NestJS log. Signing in with an unconfirmed address sends a fresh link.
- Sign-in, sign-up, forgot and reset are rate-limited in memory per address and IP (`api/src/common/rate-limit.ts`).
- In the browser use `lib/customer-auth.ts`: `useCustomer()` / `getCustomer()` (`GET /api/auth/me`, one request per page load), `accountApi()` for `/api/auth/*` and `/api/account/*`, `announceAuthChange()` after sign-in or a profile change, `signOut()`.
- The shopper's own data goes through `/api/account/*` (`api/src/storefront/account.controller.ts`), which takes the user from the session: favorites (`lib/favorites.ts`), their orders (settings page), posting a review (under the account's name).

   **When you add a back-office page, give it a rule in `PAGE_PERMISSIONS` (and a menu permission in `MENU_PERMISSIONS` in `app/admin/layout.tsx`); when you add an API route or method, give it a rule in `apiRequirement` or a decorator.** The guard denies routes that have neither.
2. **Locale prefixing.** Every storefront page lives under `app/[locale]/`. A path with no locale is redirected to one detected from `Accept-Language`. `/admin`, `/api`, and `/api-docs` are left unlocalized.

### Internationalization

The supported locales are `en`, `fr`, and `ar`, and the **default is `ar`** (RTL). All of this is defined in `lib/language-utils.ts` (`isRTL`, `detectLanguageFromHeader`, `isValidLocale`). `next-intl` is installed but largely unused. The actual i18n works like this:
- Locale comes from the route param and is exposed to client components through `LanguageProvider` / `useLanguage()` (`lib/language-context.tsx`).
- UI strings sit in inline per-component `translations = { en, fr, ar }` objects.
- `<html lang>` comes from the `x-locale` header set in `middleware.ts`, and `LanguageProvider` updates it after client-side locale switches. RTL is applied per section with `isRTL()`, not on `<html dir>`.
- The home page is configured in Admin → Landing page (`/api/landing`, `marketing` permission). Section order and visibility, list sizes, autofill and the spotlight category are stored in the `site_settings` row `landing_config` (JSON, shape and defaults in `lib/landing-config.ts`). Product picks are stored in `landing_products` (sections `new_arrivals`, `showcase`, `ring`, `top_products`, `promo_products`, `spotlight`, saved through the `set_landing_products` RPC). Featured categories use `categories.featured_position` (`set_featured_categories`). In every list, pinned products come first, then the automatic choice if autofill is on. `app/[locale]/page.tsx` renders the sections in the configured order. When you add a home section, add its key to `HOME_SECTIONS`.
- `hero_sections.sort_order` controls placement: 0–1 are the right-hand cards, 2 is the left card, and 3 and above are carousel slides.
- Database content has per-locale columns (`name`, `name_ar`, `name_fr`, `description_ar`, …). Pick the right one with the helpers in `lib/utils/product-utils.ts`, which fall back to the base column.

### Database access

NestJS connects to Postgres as the owner of the tables (`api/src/db/database.ts`: Kysely on `pg`), so row-level security (still enabled, no policies) doesn't filter it and no other role can read anything. Browsers never reach the database: everything goes through `/api`.
- Every read must filter `deleted_at is null` itself, embeds included (`one()` / `many()` in `api/src/db/embed.ts`).
- Writes go through `db.withActor(actor | null, trx => …)`, which sets the settings the activity log reads (see Activity log). `null` (checkout, webhooks, scripts) means no staff member: the change isn't logged.
- `db.call(name, params, trx)` calls a database function with named arguments, encoded by their declared types.
- Checkout: `lib/orders.ts` `createOrder` calls `POST /api/orders`, which takes `user_id` from the session cookie.

**Related writes must be one transaction.** Any operation that writes more than one row/table that belong together is a Postgres function (`supabase/migrations/20261001170000_transactional_writes.sql` and later ones), called from NestJS with `db.call()`:
- `create_order` (order + lines)
- `set_order_status` (status + stock movement)
- `delete_orders` (stock restore + mark cancelled and deleted, one or many)
- `save_product` (product, variants, variant photos, photos, opening stock, tracking, importer discount; create and update)
- `record_stock_movements` (all movement types, counts across locations, tracking flag)
- `save_landing_page` (Admin → Landing page: a section's picks, `landing_config` and featured categories)
- `delete_variant` (variant + its photos)
- `purge_deleted` (permanent deletes, see below)

If any step fails, nothing is written. Bulk deletes send `?ids=a,b` and run one statement. When you add a write that touches several rows or tables together, add or extend such a function rather than chaining client calls.

**No hard deletes.** Deleting means `deleted_at = now()`, plus `status = 'archived'` / `active = false` / `is_available = false` where the table has one (orders become `cancelled`). The trigger `private.prevent_hard_delete` rejects `DELETE` on every business table with `hard_delete_not_allowed`. The one way past it is `public.purge_deleted(table, ids)` (NestJS only), which erases rows that are **already** soft-deleted, along with what cascades from them, and logs each one as `purge`. Admins and staff with the `hard_delete` permission use it from Admin → Deleted items (`/api/admin/trash`, which also needs the table's area permission; the table list is `lib/trash-tables.ts` and must match the function's). The only exception is `inventory_levels`, which the stock trigger maintains; accounts are `public.users` rows, soft-deleted like the rest (their sessions revoked). Every read must add `deleted_at is null`, including on embeds. Favorites are removed by setting `deleted_at` and re-added by upsert. Team members are soft-deleted by the Team API (`api/src/admin/team.controller.ts`).

**Activity log.** `activity_log` is append-only and filled by the trigger `private.log_activity` on business tables. Each row records the staff member, the action (create/update/delete/restore) and the changed columns as before → after. The actor comes from the transaction settings `request.jwt.claims` / `request.headers` (`x-actor-*`), read by `private.trusted_request_headers()`; NestJS sets them in `db.withActor()` (the names come from the PostgREST days). Writes without a staff member (checkout, scripts that set the same settings, like the WooCommerce importer) aren't logged; direct database edits are logged with `source = 'database'`. Team changes are logged by the Team API itself (action create/update/remove_access/delete, entity `team_member`). Admins browse the log in Admin → Activity (`/api/admin/activity`). The identity comes from the verified session, never from request headers.

**Notifications.** The `notifications` table holds one row per recipient, with the title and body stored in en/fr/ar (`private.i18n`).
- **New orders:** a deferred trigger on `orders` notifies the owners, the admins, and staff with `orders`.
- **Owner alerts:** the trigger `private.owner_alerts` on `activity_log` notifies owners about what admins and staff do: deletes (grouped per person over 10 minutes, plus a critical alert past 10), purges, blocked attempts (middleware logs `access_denied`), team changes, price cuts of 50% or more, discounts of 50% or more, stock adjustments of 20+ units, settings changes, cancelled or refunded orders, and restores. Owners' own actions don't alert. Admins receive these alerts while no owner exists.
- **Recipients:** they come from `back_office_users`, which `GET /api/admin/me` and the Team API keep in sync (it includes roles set through `OWNER_EMAILS` / `ADMIN_EMAILS`).
- **Delivery (NestJS, `api/src/notifications/notification-events.ts`):** the trigger `private.announce_notification` sends each new or changed row's id on the Postgres channel `notifications`. NestJS LISTENs (`LISTEN_DATABASE_URL` when `DATABASE_URL` is a transaction pooler), streams the row to the recipient's open admin tabs through `GET /api/admin/notifications/stream` (SSE, `{ op, row }`, closed every 15 minutes so the session is re-checked), and sends new rows as Web Push. One API instance is assumed.
- **In the admin:** the header bell (`components/admin/NotificationBell.tsx`) loads `/api/admin/notifications`, listens on the stream (pop-up and sound), and reloads every 60 seconds as a safety net.
- **Desktop push:** NestJS sends Web Push (`web-push`) to the recipient's `push_subscriptions`, shown by `public/admin-sw.js`, with `VAPID_KEYS` (JWK pair, the Edge Function's format) and `VAPID_SUBJECT`. The browser key is the `vapid_public_key` row in `site_settings`; it must match `VAPID_KEYS`. Expired subscriptions (404/410) are soft-deleted.
- **Adding an alert:** add a rule to `private.owner_alerts`, or call `private.notify(recipients, …)` from SQL.

**The schema source of truth is `supabase/migrations/`.** The legacy SQL scripts from the old project have been removed. Categories are nested (`categories.parent_id`): use `getDescendantCategoryIds` (`lib/utils/product-utils.ts`) wherever products are filtered by category. For a new migration, add `supabase/migrations/<yyyymmddhhmmss>_<name>.sql` (plain Postgres SQL; the folder keeps its old name) and apply it with `api/scripts/migrate.mjs`. The older migrations are the history and only applied on Supabase; a new database is built by copying one with `scripts/db/move-database.mjs`. **Files** live in S3-compatible storage (AWS S3, signed with the server's instance role; a local SeaweedFS in Docker), through `api/src/common/storage.ts`: bucket `products` (public, at `FILES_PUBLIC_URL`; real names in `S3_PRODUCTS_BUCKET` / `S3_DOCUMENTS_BUCKET`; uploads through `POST /api/upload/image`) and `documents` (private). `api/scripts/copy-storage.mjs` copied the Supabase buckets over and, with `--rewrite`, replaced the old image URLs in the database (not in `activity_log`).

### Data and business logic

- Discounts live only in `product_discounts`, and the product row has no discount column. Every listing attaches them with `activeDiscounts()` (`api/src/sales/commerce.ts`), or prices show undiscounted.
- `lib/product-search.ts` (`MIN_SEARCH_LENGTH`) and `GET /api/storefront/products?search=`: product search, used by the header suggestions (`components/layout/SearchBox.tsx`) and the products page. Matching runs in Postgres through `search_products(query)`, which returns ranked ids of live products. It searches `products.search_text`, which a trigger keeps up to date with the names, descriptions and code in all three languages plus the category and parent-category names, all run through `normalize_search_text` (lower case, no accents, Arabic diacritics removed and letter variants unified). Every word must match, in any order, and name matches rank higher. When nothing matches, it falls back to similar spellings with pg_trgm. A search with no explicit sort is shown in relevance order. If you add a searchable field, add it to `private.set_product_search`.
- Shipping cost, the free-shipping threshold, and per-country tax rates come from the `site_settings` key/value table, `shipping_rates`, and `country_tax_rates`, with hard-coded fallbacks (`siteSettings()`, `calculateShipping()`, `countryTaxRate()` in `api/src/sales/commerce.ts`).
- `lib/orders.ts` → `POST /api/orders` → `priceOrder()` (`api/src/sales/commerce.ts`): checkout is re-priced on the server and nothing client-supplied is stored as an amount.
  - Each unit price must match `round(base or variant price × (1 − valid discount%))`, which is how the product pages build cart prices.
  - Subtotal, shipping and tax are recalculated, and item names and images come from the catalog.
  - Mismatches return 409 with `code`: `PRICES_CHANGED`, `TOTALS_CHANGED` or `PRODUCT_UNAVAILABLE`, which the checkout maps to translated messages.
  - If you change how the storefront computes a price, update `priceOrder()` too.
- `lib/order-confirmation-email.ts`: sent from `POST /api/orders` using the stored order, with customer text HTML-escaped. There is deliberately no public "send email" endpoint. `abandoned-cart-email.ts` is also here. Both send through nodemailer/Gmail SMTP (`GMAIL_USER`, `GMAIL_APP_PASSWORD`).
- `cart-context.tsx`: the cart is client-side only (localStorage key `shopping_cart`), provided in `app/[locale]/layout.tsx` along with `CartDrawer`. Lines are keyed by product + variant (`cartLineKey`); `removeItem`/`updateQuantity` take that key. Product cards add through `useQuickAdd()` (`lib/quick-add.ts`), which opens the product page when a size/color must be chosen.

### Stock

Stock management (formerly a separate app) lives in this database and the admin's Stock section.
- **Never write `product_variants.stock` or `inventory_levels` directly.** Every change is a row in the append-only `stock_movements` (types `restock`, `sale`, `return`, `adjustment`, `transfer`); the trigger `private.apply_stock_movement` updates `inventory_levels` (per variant × location) and rejects negative stock with `insufficient_stock:<sku>:<available>` (`stockErrorMessage()` in `lib/stock.ts` turns it into a message). Record movements through `POST /api/stock/movements` (also does transfers and `count` mode).
- One location has `sells_online`. For products with `stock_tracked = true`, its levels are mirrored into `product_variants.stock`, which the storefront and checkout read. Every product stays orderable whatever `stock` says. A tracked product with no stock shows as made to order ("Sur commande" / "حسب الطلب") on the product page instead of out of stock; in stock means `!stock_tracked || stock > 0`.
- Orders: the admin shows `processing` as **Validated**. The "Validate" button (`validateOrder` in `components/admin/order-status.ts`, `POST /api/delivery` action `validate`) creates the order's Colissimo parcel and moves the order to `processing` (without Colissimo tokens it only validates). The status dropdown on the order page is a manual override and creates no parcel. `order_items` store `variant_id` and `variant_label`. `PUT /api/orders` calls `apply_order_stock` (idempotent via `orders.stock_deducted`): processing/shipped/delivered deducts tracked items from the online location, but only the units it holds (the rest is made to order), and pending/cancelled restores exactly what was deducted. Checkout (`order-pricing.ts`) accepts lines over stock and rejects only tracked multi-variant lines without a variant (`VARIANT_REQUIRED`).
- Delivery (Colissimo): Admin → Delivery (`/admin/delivery`) and the order page's delivery card send orders through `/api/delivery` (`orders` permission), using `lib/colissimo.ts` (tokens `COLISSIMO_ADD_TOKEN` (full) and `COLISSIMO_TRACKING_TOKEN` (read-only); governorate names and statuses in `lib/colissimo-data.ts`). Parcels are created with Colissimo's v1 API (`post.php`); everything else uses the v2 API (`/apis-v2`: batch tracking, `validate_orders` hand-over, `edit_order`, `price_change`, `delete_order`; JSON, `X-Api-Key`, stable `error_code`, RATE_LIMIT/DB_ERROR retried once). It can't list an account's parcels, so the `deliveries` table is the parcel list; parcels made on Colissimo's site are added by barcode, "Check a parcel" looks up any barcode without saving (action `track`), and "New parcel" creates one by hand. When "New parcel" lists products (priced by `buildManualOrderLines()`, previewed with action `quote`), Colissimo is called first and then `create_order_with_delivery` saves the order, its lines and the parcel and validates the order (stock) in one transaction, recording the agent in `orders.created_by` / `created_by_email` (null for website orders). Admin → Agent performance (`/admin/performance`, `GET /api/admin/performance`, owners and admins) compares agents with `agent_performance(from, to)`; the orders list filters by agent (`?added_by=<user id>` or `website`). Sending is `begin_delivery` (reserves the order's single live parcel row) → Colissimo → `complete_delivery` (barcode + pending order validated), or `fail_delivery`. The parcel fields come from `parcelFromOrder()`; when one is missing (`NEEDS_DETAILS`, e.g. an old order without a governorate) the admin completes them in the send form. Tracking (`ColissimoTracking`, `api/src/sales/colissimo-tracking.ts`) checks every parcel that can still change every 15 minutes (and on Refresh) and writes only changes (`record_delivery_status`): picked up / at the depot / out for delivery marks a validated order shipped, delivered (`Livre` v1, `Livrer` v2) delivered, delivered and paid (`Livre paye`, or `Livrer` with `deliveries.paid`) also records the cash still owed as a payment held by the carrier (see Money below), once, and a final return status (`Retour definitif`, `Retour paye`, `Retour recu paye`, `Rtn definitif`, `Retour recu`) marks the order returned, which puts its stock back; the driver's live report is kept in `driver_status`. Parcels waiting for pickup are handed over in a manifest (action `handover`), edited at Colissimo and on the order (`edit`; once printed a price becomes a `price_change` request, kept in `deliveries.price_change`), and deleted at Colissimo when their order is cancelled or deleted, or the parcel is removed (Colissimo refuses once it has the parcel; those stay listed). Shoppers see their parcel's stage in their account (`delivery` on `/api/account/orders`, `customerStage()`, `components/ui/OrderTracking.tsx`). Locally and in CI the API talks to a stand-in (`scripts/docker/colissimo-mock.mjs`, the `colissimo` compose service, tested by `api/test/e2e/colissimo.e2e.mjs`). Checkout collects what Colissimo needs: governorate (`shipping_state`, stored with Colissimo's spelling from `governorateOptions()`), city and address, all required.
- Product saves (`save_product`, used by `POST/PUT /api/products` and the importer) update variants in place, matched by id or color + size, because variant ids carry stock. Removing a variant that still holds stock is refused with 409. New products record their opening stock as restock movements and start tracked.
- Product codes and variant SKUs are generated by triggers when left blank. Purchase costs live in `product_costs` (`costs` permission).
- **Each product has one cost: `product_costs.cost`** (the "Purchase cost (per unit)" field on the product form, `costs` permission). It's the basis of margins, cost of goods, stock value and statistics: `variant_unit_cost()` returns it, falling back to `product_variants.avg_cost` (the weighted average of restocks with a `unit_cost`, kept by `private.stock_movement_cost`) only for products without one. Order lines store `unit_cost` when created; when a product gets its cost, its lines that had none take it (`private.fill_order_item_costs`), and the owner overview falls back to the current cost for any line still without one. Saving a bill of materials (`save_product_costing`) sets the product's cost to materials + labor + overhead.
- `lib/schemas/`: zod schemas used with react-hook-form (for example, checkout).

### ERP: sales pipeline, customers, till, purchasing, money

Migrations `20261016120000_erp_sales_crm`, `…121000_erp_purchasing_pos` and `…122000_erp_accounting`. NestJS routes validate with the `Zod` pipe and refuse with `ApiError` (`api/src/common/api.ts`; zod errors and known database exceptions become 4xx with a message in `DB_MESSAGES`, `lib/erp/db-messages.ts`); shared values and labels are in `lib/erp/constants.ts`; admin screens use `components/admin/erp/*` (`api()`, `useApi()`, `formatMoney()` with 3 decimals, `PageHeader`, `Kpi`, `PeriodFilter`, `AgentSelect`, dependency-free SVG `BarChart` / `BarList` / `TargetBar`). Business rules a person can change are in `erp_settings` (admin only; `site_settings` is read by the storefront), edited in Admin → Business settings and Accounting → Settings.
- **Orders pipeline.** `orders.status`: `pending` (to confirm) → `confirmed` (customer agreed) → `processing` (validated: parcel, stock out) → `shipped` → `delivered`, or `returned` (stock back) / `cancelled`; `set_order_status` stamps `confirmed_at`, `delivered_at`, `returned_at`, `cancelled_at`. Orders also carry `channel` (website, facebook, instagram, tiktok, whatsapp, phone, store, other), `campaign_id`, `assigned_to` (the agent handling it; `agent_performance` and objectives use `coalesce(assigned_to, created_by)`), `discount_amount` (total = subtotal − discount + shipping), and `location_id` (stock source; null = online location). Agents create orders in Admin → New order (`POST /api/sales/orders`, priced by `buildManualOrderLines()` in `api/src/sales/commerce.ts`), and `PATCH /api/sales/orders` assigns, confirms and sets the source. Discounts above `erp_settings.pos.max_discount_percent` need an owner or admin (also at the till).
- **Duplicates.** `find_order_duplicates(phone)` lists open orders from the same phone (`normalize_phone`: 8 Tunisian digits); the New order form and the orders list warn about them.
- **Customers (CRM).** `customers` has one live row per normalized phone; the trigger `private.link_order_customer` links every new order to it (creating it), and `sync_customer_stage` moves its `stage` with its latest order (`new` / `interested` are set by hand). Conversations are `customer_interactions` (direction in/out/note), follow-ups `crm_tasks`. `merge_customers`, `find_customer_duplicates`, `anonymize_customer` (personal-data erasure). Meta channels are optional: `POST /api/webhooks/meta` (public, signature-checked with `META_APP_SECRET`; `META_VERIFY_TOKEN`) stores incoming Messenger/Instagram/WhatsApp messages, and replies go out through `lib/erp/meta.ts` (`META_PAGE_ACCESS_TOKEN`, `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`). Without them the CRM works by hand.
- **Money is not delivery.** Each payment received is an `order_payments` row (negative: refund) with `account` cash, bank or carrier (cash on delivery Colissimo still holds); `orders.paid_amount` / `payment_status` (`pending`, `partial`, `paid`, `refunded`) follow them through a trigger — don't set them by hand. A carrier payout (`record_remittance`, `cod_remittances` with fees) clears the carrier balance. `treasury_movements` are the other cash/bank movements (opening balance, owner, loans, transfers via `record_cash_transfer`, till differences). `treasury_balances()` sums it all.
- **Till.** `pos_sessions` per shop location (one open at a time): `open_pos_session` → `create_pos_sale` (an order of channel `store`, delivered at once, stock from the session's location, payments) → `close_pos_session` (counted vs `pos_expected_cash`, the difference booked as a movement). Receipts: `/admin/pos/receipt/[id]`.
- **Purchasing.** `purchase_orders` (+ lines: variants, raw materials or free text; status `draft` / `rfq` price request / `ordered` / `partial` / `received` / `cancelled`) saved with `save_purchase_order`; goods arrive through `purchase_receipts` (accepted / rejected per line) and enter stock only when validated (`validate_purchase_receipt`, at the order's unit cost). `purchase_price_comparison()`. Raw materials have their own append-only `material_movements`; cost price per model = bill of materials (`product_bom`) + `product_costing` labor/overhead (`product_cost_prices()`); `record_production` consumes materials and restocks finished units at cost price.
- **Accounting (Tunisian SCE).** `accounts` (seeded chart; `is_system` ones are used by automatic entries, mapped in `erp_settings.accounting.accounts`), `journal_entries` + `journal_lines`. Triggers book entries with `private.book()` / `private.unbook()`: delivered order → sale (VT, prices include VAT at `sales_vat_rate`), payments (CA/BQ/OD), carrier payouts (fees → 6241), `bills` (AC; supplier invoices and expenses) and `bill_payments`, treasury movements, `ad_spend`, invoice stamp duty. Nothing is booked before `accounting.start_date`. Entries start as drafts; `post_journal_entries` numbers them per journal and year (gap-free `private.next_number`) and freezes them (`protect_posted_entry`); corrections are reversals. Purchases are expensed on their bill and `book_stock_variation` adjusts stock accounts at period end (intermittent inventory). Reports: `trial_balance`, `vat_summary`, and `/api/finance/reports` (ledger, income statement, balance sheet, FEC-style CSV export). `sales_invoices` (FA-/AV- numbers, `issue_invoice`, `cancel_invoice` by credit note) never change once issued. `bank_statement_lines` + `auto_match_bank` reconcile the bank. `documents` live in the private `documents` bucket (S3, links signed for 5 minutes).
- **Owner overview and objectives.** `owner_overview(from, to, channel, agent, product, campaign)` feeds Admin → Business overview (`/api/owner/overview`, owners only): delivered sales, gross margin (from `order_items.unit_cost`), estimated net margin (− ads, bills except stock purchases, carrier fees), money collected, cash/bank/carrier, receivables, supplier debts, stock value, rates, and breakdowns. `business_goals` holds the whole business's goal per month (delivered sales, gross margin, orders taken/confirmed/delivered, highest return rate, ad budget), set in Admin → Objectives & commissions (`PUT /api/admin/goals`); `teamProgress()` in `lib/erp/goals.ts` measures it with `owner_overview` over the month (Tunis time) and the pace so far, shown on that page, the Business overview and My day (`MonthGoalCard`). `agent_goals` (set with `set_agent_goal`) hold each member's monthly targets and commissions (`monthProgress()`); agents see theirs on My day (`/api/admin/my-work`). Commissions (`commissionFor()` in `lib/erp/objectives.ts`, shared by `api/src/admin/goals.ts` and `main`'s Next.js routes): % of delivered sales, an amount per delivered order, or **prize tiers** (`agent_goals.prize_tiers`, e.g. 50 delivered orders → 100 TND, 80 → 200 TND: the highest tier reached pays). Objectives also show orders delivered per day and the prizes to pay. **Analytics reset:** Business settings → Analytics stores `erp_settings.analytics.start_date`; the Business overview, Agent performance, Objectives and My day count only from that date (`clampToStart()`); nothing is deleted, and clearing it shows the full history.
- **Alerts.** `private.daily_alerts()` (run by NestJS every day at 07:00 UTC) notifies orders waiting too long, late deliveries, follow-ups due, bills due within 3 days and expiring documents; low stock (`notify_low_stock`) and incoming customer messages notify immediately.

### Caching and performance

- **Next.js data cache.** `lib/catalog-cache.ts` wraps public catalog reads in `unstable_cache` with the `catalog` tag and a 5-minute safety revalidate. It covers the product page (`getCachedProductDetail`, from the loader in `lib/product-detail.ts`) and all home page data. The home loaders in `lib/home-data.ts` (featured categories, top and promo products, sale banners, reels, latest reviews) plus the landing and hero data are loaded in `app/[locale]/page.tsx` and passed to the sections as `initial*` props, so they render in the first HTML. Keep new home sections on this pattern instead of fetching in `useEffect` behind a `mounted` flag. `/api/products/top` and `/promo` serve the same cached loaders.
- **Invalidation.** Every admin mutation route (products, variants, product-images, promotions, categories, colors, sizes, sale-banners, stock movements and tracking) calls `invalidateCatalog()` before returning success. **New admin write routes must do the same**, or the storefront serves stale data. Writes that bypass the API (the importer, direct database edits) show up after at most 5 minutes.
- **Product page.** `app/[locale]/products/[slug]/page.tsx` is a server component that passes cached data to `ProductDetailClient.tsx`. It only fetches reviews client-side.
- **Header and footer** are rendered once in `app/[locale]/layout.tsx`. Don't add `<StaticHeader />` or `<Footer />` to pages.
- **Browser-side caching.** `lib/categories-cache.ts` shares the category list across pages. `next.config.ts` sets `staleTimes` so the client router cache makes revisits instant.
- **Admin lists** use `GET /api/products?admin=true&view=summary` (no variants, about 50 KB). The full payload is about 1 MB, so use it only for a single product (`?id=`).
- **Middleware auth** verifies the `kb_access` JWT locally with `AUTH_SECRET`: no network call, except one refresh every 15 minutes per session.
- `next dev` roughly doubles API calls (React Strict Mode effects) and compiles pages on demand, so judge performance on a production build.

### Admin

Ant Design is used **only in the admin**; the storefront uses Tailwind plus `react-hot-toast`. Don't import `antd` in `app/[locale]` or `components/` outside `components/admin`, because it adds about 500 kB to every page. In admin forms, an `InputNumber` inside `Space.Compact` must sit in a `noStyle` `Form.Item` (see the Base Price field), or the value never reaches the form. Import `message` from `@/components/admin/antd-app`, not from `antd`: the admin layout wraps pages in antd's `<App>`, and the static API ignores the theme and warns. For searchable `Select`s whose values are ids, give options a `searchtext` and use `filterOption={searchByText}` (`components/admin/select-search.ts`). The admin layout installs `components/admin/admin-fetch-cache.ts`, which keeps the small lookup lists (categories, colors, sizes, suppliers, collections, locations) in memory for 5 minutes and clears an entry on any write to the same path. `app/admin/` is a client-rendered Ant Design dashboard (layout in `app/admin/layout.tsx`, theme in `lib/antd-config.ts`). It covers products, variants, categories, orders, stock (inventory, movements, restock, settings), team, promotions, sale banners, reels, and cart analytics, and it reads and writes through `/api` (NestJS).

**Admin language (EN / FR / AR).** The admin has its own language switch in the header (and on the login page), separate from the storefront URL locale. It's remembered per browser:
- Write UI text in English and wrap it: `const { t } = useAdminT()` then `t("Save changes")` or `t("Deleted {count} color(s)", { count })`.
- Text defined outside components (constants) is marked with `msg("…")` and translated where it's displayed with `t(value)`.
- French and Arabic live in `lib/admin-translations.ts` as `[English, French, Arabic]` rows (the ERP screens' rows are in `lib/admin-translations-erp.ts`, merged in; the original table wins on duplicates). A missing row falls back to English, so **add a row for every new string**, keeping `{placeholders}` intact.
- Arabic switches antd and the layout to right-to-left; antd's own texts (pagination, OK/Cancel, dates) and dayjs follow the language (`AdminConfig` in `app/admin/layout.tsx`).
- Never translate values that are data (HTTP methods, statuses sent to the API, ids).

### API docs

`lib/openapi.ts` builds an OpenAPI spec by hand (ERP routes in `lib/openapi-erp.ts`). `/api/docs` serves it and `/api-docs` renders it with swagger-ui. If you change an API route's shape, update this spec too.

### NestJS API

`api/` is the NestJS 11 app behind every `/api` request (conventions in `api/README.md`; the history of the move is in `docs/MIGRATION-NESTJS.md`). `next.config.ts` rewrites `/api/:path*` to `NEST_URL` (afterFiles, so `app/api/internal/revalidate`, the one route left in Next.js, still answers). The storefront needs NestJS running wherever it is deployed.
- Access rules: a decorator on the route (`@Public`, `@Requires`, `@RequiresAll`, `@AdminOnly`, `@OwnerOnly`) and/or `apiRequirement` in `lib/api-access.ts`; the guard (`api/src/auth/auth.guard.ts`) applies both and denies a route that has neither.
- NestJS catalog writes refresh the storefront cache through `POST /api/internal/revalidate` (`REVALIDATE_SECRET`).
- The storefront's public reads come from `/api/storefront/*` through `lib/storefront-api.ts`: on the server via `NEST_URL`, in the browser through the rewrite.
- `api/` imports root `lib/` files as `@shared/*`; a shared file may only use relative imports (`lib/admin-auth.ts`, `lib/erp/db-messages.ts`, `lib/stock.ts`).
- Root `npx tsc --noEmit` and lint skip `api/`; check it with `npm run build` and `npm run lint` in `api/`. `api/test/e2e` holds the end-to-end suites (`node test/e2e/<suite>.e2e.mjs` in `api/`, against the local Docker stack and its database only).

## Configuration notes

- The env var names are listed in `ENV-EXAMPLE.md`. `ADMIN_EMAILS` and `SUPABASE_SERVICE_ROLE_KEY` are server-only. `AUTH_SECRET` (signs sessions) must be the same on the Next.js server and NestJS.
- `ENV` is the deployment environment: `local` on developer machines, `production` on the server. `next.config.ts` passes it to all code as `NEXT_PUBLIC_APP_ENV`; read it through `APP_ENV` / `isProduction` / `isLocal` in `lib/app-env.ts` rather than `NODE_ENV`, which is `production` for any build, including local ones.
- Fonts are self-hosted with `next/font/local` (`app/fonts/*.woff2`: Inter and Handlee Latin subsets, Reem Kufi Arabic + Latin, variable weights) and wired in `app/layout.tsx` and `lib/fonts.ts`. Don't switch back to `next/font/google`: Turbopack fails the build when the Google Fonts download is slow or offline.
- `next.config.ts` whitelists remote image hosts, including the file storage at `FILES_PUBLIC_URL` (read at build time). Add any new image source there.
- **Error monitoring (Sentry, `@sentry/nextjs` v11).** Init files: `instrumentation-client.ts`, `sentry.server.config.ts`, `sentry.edge.config.ts`, loaded by `instrumentation.ts` (which also reports request errors); shared options and the PII scrubber are in `lib/sentry-options.ts`. It only reports from production builds (never `next dev`) with `NEXT_PUBLIC_SENTRY_DSN` set, and its environment tag and sample rates follow `ENV`. Thrown errors are captured automatically; where an error is caught and turned into a response or fallback, call `reportError(error, area)` from `lib/report-error.ts`, and never pass customer details. Browser events go through the `/monitoring` tunnel, which the middleware matcher excludes. In v11, `withSentryConfig` is imported from `@sentry/nextjs/config`.
- The many top-level `*.md` files are historical setup and fix notes. Treat them as background, not as the current source of truth.
