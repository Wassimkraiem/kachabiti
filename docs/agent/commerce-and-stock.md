# Pricing, checkout, cart, stock, orders and Colissimo delivery

Moved verbatim from CLAUDE.md so it loads only when needed. Keep it accurate when you change this area.

### Data and business logic

- Discounts live only in `product_discounts`, and the product row has no discount column. Every listing attaches them with `activeDiscounts()` (`api/src/sales/commerce.ts`), or prices show undiscounted.
- `lib/product-search.ts` (`MIN_SEARCH_LENGTH`) and `GET /api/storefront/products?search=`: product search, used by the header suggestions (`components/layout/SearchBox.tsx`) and the products page. Matching runs in Postgres through `search_products(query)`, which returns ranked ids of live products. It searches `products.search_text`, which a trigger keeps up to date with the names, descriptions and code in all three languages plus the category and parent-category names, all run through `normalize_search_text` (lower case, no accents, Arabic diacritics removed and letter variants unified). Every word must match, in any order, and name matches rank higher. When nothing matches, it falls back to similar spellings with pg_trgm. A search with no explicit sort is shown in relevance order. If you add a searchable field, add it to `private.set_product_search`.
- Shipping cost, the free-shipping threshold, and per-country tax rates come from the `site_settings` key/value table, `shipping_rates`, and `country_tax_rates`, with hard-coded fallbacks (`siteSettings()`, `calculateShipping()`, `countryTaxRate()` in `api/src/sales/commerce.ts`).
- `lib/orders.ts` → `POST /api/orders` → `priceOrder()` (`api/src/sales/commerce.ts`): checkout is re-priced on the server and nothing client-supplied is stored as an amount.
  - Each unit price must match `round(base or variant price × (1 − valid discount%))`, which is how the product pages build cart prices.
  - Subtotal, shipping and tax are recalculated, and item names and images come from the catalog.
  - Mismatches return 409 with `code`: `PRICES_CHANGED`, `TOTALS_CHANGED` or `PRODUCT_UNAVAILABLE`, which the checkout maps to translated messages.
  - If you change how the storefront computes a price, update `priceOrder()` too.
- `lib/order-confirmation-email.ts`: sent from `POST /api/orders` using the stored order, with customer text HTML-escaped. There is deliberately no public "send email" endpoint. `abandoned-cart-email.ts` is also here. Both send through nodemailer: Gmail SMTP (`GMAIL_USER`, `GMAIL_APP_PASSWORD`), or another mailbox's SMTP when `SMTP_HOST` is set (port 465, TLS; same two variables as its login).
- `cart-context.tsx`: the cart is client-side only (localStorage key `shopping_cart`), provided in `app/[locale]/layout.tsx` along with `CartDrawer`. Lines are keyed by product + variant (`cartLineKey`); `removeItem`/`updateQuantity` take that key. Product cards add through `useQuickAdd()` (`lib/quick-add.ts`), which opens the product page when a size/color must be chosen.

### Stock

Stock management (formerly a separate app) lives in this database and the admin's Stock section.
- **Never write `product_variants.stock` or `inventory_levels` directly.** Every change is a row in the append-only `stock_movements` (types `restock`, `sale`, `return`, `adjustment`, `transfer`); the trigger `private.apply_stock_movement` updates `inventory_levels` (per variant × location) and rejects negative stock with `insufficient_stock:<sku>:<available>` (`stockErrorMessage()` in `lib/stock.ts` turns it into a message). Record movements through `POST /api/stock/movements` (also does transfers and `count` mode).
- One location has `sells_online`. For products with `stock_tracked = true`, its levels are mirrored into `product_variants.stock`, which the storefront and checkout read. Only products with `products.made_to_order` (the switch on the product form; the kachabiya zemniya, demi zemniya and burnous) stay orderable without stock and show as made to order ("Sur commande" / "حسب الطلب"); any other tracked product at zero shows out of stock, and checkout refuses more than the variant's stock with 409 `OUT_OF_STOCK`. In stock means `!stock_tracked || stock > 0`.
- Orders: `unreachable` (**Injoignable**, the customer doesn't answer) is still to confirm: stock in, counted and alerted with `pending`, editable, confirmable (`TO_CONFIRM_STATUSES`; PATCH `/api/sales/orders` action `unreachable`), never validated before the customer confirms. The admin shows `processing` as **Validated**. The "Validate" button (`validateOrder` in `components/admin/order-status.ts`, `POST /api/delivery` action `validate`) creates the order's Colissimo parcel and moves the order to `processing` (without Colissimo tokens it only validates). The status dropdown on the order page is a manual override and creates no parcel. `order_items` store `variant_id` and `variant_label`. `PUT /api/orders` calls `apply_order_stock` (idempotent via `orders.stock_deducted`): processing/shipped/delivered deducts tracked items from the online location, but only the units it holds (the rest is made to order), and pending/cancelled restores exactly what was deducted. Checkout (`order-pricing.ts`) accepts lines over stock and rejects only tracked multi-variant lines without a variant (`VARIANT_REQUIRED`).
- Delivery (Colissimo): Admin → Delivery (`/admin/delivery`) and the order page's delivery card send orders through `/api/delivery` (`orders` permission), using `lib/colissimo.ts` (tokens `COLISSIMO_ADD_TOKEN` (full) and `COLISSIMO_TRACKING_TOKEN` (read-only); governorate names and statuses in `lib/colissimo-data.ts`). Parcels are created with Colissimo's v1 API (`post.php`); everything else uses the v2 API (`/apis-v2`: batch tracking, `validate_orders` hand-over, `edit_order`, `price_change`, `delete_order`; JSON, `X-Api-Key`, stable `error_code`, RATE_LIMIT/DB_ERROR retried once). It can't list an account's parcels, so the `deliveries` table is the parcel list; parcels made on Colissimo's site are added by barcode, "Check a parcel" looks up any barcode without saving (action `track`), and "New parcel" creates one by hand. When "New parcel" lists products (priced by `buildManualOrderLines()`, previewed with action `quote`), Colissimo is called first and then `create_order_with_delivery` saves the order, its lines and the parcel in one transaction, leaving the order to validate (an agent's Validate later uses that parcel and takes the stock out), recording the agent in `orders.created_by` / `created_by_email` (null for website orders). Admin → Agent performance (`/admin/performance`, `GET /api/admin/performance`, owners and admins) compares agents with `agent_performance(from, to)`; the orders list filters by agent (`?added_by=<user id>` or `website`). Sending is `begin_delivery` (reserves the order's single live parcel row) → Colissimo → `complete_delivery` (barcode + pending order validated), or `fail_delivery`. The parcel fields come from `parcelFromOrder()`; when one is missing (`NEEDS_DETAILS`, e.g. an old order without a governorate) the admin completes them in the send form. Tracking (`ColissimoTracking`, `api/src/sales/colissimo-tracking.ts`) checks every parcel that can still change every 5 minutes when Colissimo's website login isn't set (the account sync below does it then), and on Refresh, and writes only changes (`record_delivery_status`): picked up / at the depot / out for delivery marks a validated order shipped, delivered (`Livre` v1, `Livrer` v2) delivered, delivered and paid (`Livre paye`, or `Livrer` with `deliveries.paid`) also records the cash still owed as a payment held by the carrier (see Money below), once, and a final return status (`Retour definitif`, `Retour paye`, `Retour recu paye`, `Rtn definitif`, `Retour recu`) marks the order returned, which puts its stock back; the driver's live report is kept in `driver_status`. Parcels waiting for pickup are handed over in a manifest (action `handover`), edited at Colissimo and on the order (`edit`; once printed a price becomes a `price_change` request, kept in `deliveries.price_change`), and deleted at Colissimo when their order is cancelled or deleted, or the parcel is removed (Colissimo refuses once it has the parcel; those stay listed). Shoppers see their parcel's stage in their account (`delivery` on `/api/account/orders`, `customerStage()`, `components/ui/OrderTracking.tsx`). Owners also see the whole Colissimo account in Admin → Colissimo account (`/admin/colissimo-account`, `GET /api/owner/colissimo`, 2 months at a time; `POST /api/owner/colissimo/sync` runs every 5 minutes: it adds every parcel of the account that `deliveries` doesn't have yet, unlinked, so the Delivery tab lists them all, and gives each parcel the status of the dashboard card that lists it (`cardParcels()`: attente.php, cours.php, verifier.php…, so the cards match Colissimo's dashboard) with its attempts (`deliveries.attempts`) and contents, then gives delivered parcels Colissimo's own delivery date through `redate_deliveries` (the parcel, its order's `delivered_at`, the carrier payment and their draft entries, only where the day differs; status changes are otherwise saved at the sync's time); clicking a parcel there or on the owner page shows its history from `GET /api/delivery/history?code=`, `orders` permission): `api/src/sales/colissimo-portal.ts` signs in to Colissimo's website (`COLISSIMO_PORTAL_USER` / `COLISSIMO_PORTAL_PASSWORD`, session kept in memory) and parses its pages read-only, since the API can't list parcels; a change to their pages breaks only that page. Locally and in CI the API talks to a stand-in (`scripts/docker/colissimo-mock.mjs`, the `colissimo` compose service, tested by `api/test/e2e/colissimo.e2e.mjs`). Checkout collects what Colissimo needs: governorate (`shipping_state`, stored with Colissimo's spelling from `governorateOptions()`), city and address, all required.
- Product saves (`save_product`, used by `POST/PUT /api/products` and the importer) update variants in place, matched by id or color + size, because variant ids carry stock. Removing a variant that still holds stock is refused with 409. New products record their opening stock as restock movements and start tracked.
- Product codes and variant SKUs are generated by triggers when left blank. Purchase costs live in `product_costs` (`costs` permission).
- **Each product has one cost: `product_costs.cost`** (the "Purchase cost (per unit)" field on the product form, `costs` permission). It's the basis of margins, cost of goods, stock value and statistics: `variant_unit_cost()` returns it, falling back to `product_variants.avg_cost` (the weighted average of restocks with a `unit_cost`, kept by `private.stock_movement_cost`) only for products without one. Order lines store `unit_cost` when created; when a product gets its cost, its lines that had none take it (`private.fill_order_item_costs`), and the owner overview falls back to the current cost for any line still without one. Saving a bill of materials (`save_product_costing`) sets the product's cost to materials + labor + overhead.
- `lib/schemas/`: zod schemas used with react-hook-form (for example, checkout).
